# M2: Import, mapping, validation, quarantine, deduplication

Source: `docs/plan.md` §16 (M2), with detail from §6.2 (entities), §8 (`process_import` job), §14 modules B, C and D, §15 (dependencies) and §17 (open items U2, U3, U6), and decisions D-042, D-050, D-063, D-068 to D-077, D-092, D-099, D-107 to D-111 in `docs/requirements/Q-A.md`. Nothing here is new scope. Status: **planned, not started**.

## 1. Purpose and output
M1 created the empty tables. M2 fills them: it turns a real Apollo, Excel or CSV file into clean `Person` and `Company` records, and keeps the problems visible instead of losing them. It delivers:
- file upload with duplicate-file detection, column mapping and preview,
- a background import that never fails the whole file because of bad rows,
- validation, with problem rows held in a quarantine that BD can fix, release or discard,
- person and company matching, field-level merging, and a review screen for uncertain duplicates,
- an import report (and downloadable CSVs) after every import.

It does not include lead search, lead detail screens, eligibility checks, opt-out screens or exports (M3), nor any email drafting or sending (M4 onward).

## 2. Tasks

| # | Task | What it means |
|---|---|---|
| 1 | Upload and SHA-256 | Accept CSV or XLSX (up to 50,000 rows or 20 MB, one sheet per import, D-110). Hash the file; if the same content was uploaded before, warn with the earlier date and user and offer cancel or import anyway (D-109). |
| 2 | Worksheet and profile selection | For XLSX, pick the worksheet; pick a source profile (Apollo layout, saved layouts) and a default country. |
| 3 | Mapping UI with saved mappings | Map file columns to app fields, save the mapping on the source profile, and prompt to fix missing headers. |

| 7 | Normalization | Normalize emails, domains, names, countries, states and industries (industry against a NAICS-sector list, D-076). |
| 8 | Validation rules | Apply the mandatory-field and email-type rules (section 4). |

## 3. Data model scope
No new tables are expected: the models and migrations already exist from M1 (`0006` leads, `0007` imports). M2 adds services, APIs and screens on top of them. Any schema change M2 needs is a new migration, never an edit of an applied one, and updates `database.md`.

- **imports:** `ImportFile` (sha256, filename, uploader, source profile, default country, worksheet, status, counts), `SourceProfile` (layout, mapping defaults), `ColumnMapping`, `RawRow` (file, row number, original values as JSON, never modified except by erase-person), `ImportReport` (totals and reason-coded failures), `ImportChange` (the transient per-import "what changed" summary, D-050).
- **leads:** `Company`, `Person`, `PersonEmail` (work, personal or generic; verification; primary), `PersonPhone`, `SocialProfile`, `ContactChannel` (generic channels such as info@), `QuarantineRecord` (issues, status, editable payload), `DuplicateCandidate` (pair, reason, status open / merged / not-duplicate), `MergeRecord` (survivor, absorbed, snapshot), `IndustryMapping`, `StateMapping`, plus the source engagement fields on `Person` (last contacted, sent / opened / bounced / replied / demoed, stage, lists as tags; intent signals are stored but unused, D-063, D-074).
- **compliance:** `OptOut` is written when a source row says do-not-contact (D-073).
- **audit:** quarantine discard, merge, import start and every report download are audited (D-111).

Modeling rules that apply:
- Two data layers: `RawRow` is immutable; unified `Person` and `Company` keep the latest values only, with no change history (D-008). `[AGREED]`
- Email addresses live in their own table. Secondary, tertiary and personal emails are stored but never used for outreach (D-072). `[AGREED]`

## 4. Validation and quarantine rules (module C)
- **Never reject a whole file** (D-068). Valid rows import; bad rows are quarantined.
- **Only two mandatory fields:** a valid work email and a first name (D-069).
- **Goes to quarantine:** a row whose only email is personal or free-mail, a generic role address (info@, sales@, support@), or a badly formatted email (D-042, D-072). A valid person with only an unusable email is quarantined (Q-IMPORT-17, Q-IMPORT-20).
- **Does not go to quarantine:** missing industry becomes "Unknown" (D-070); missing company name is derived from the work-email domain and marked as derived (D-071); Apollo-"unverified" emails stay eligible with a warning (D-042).
- **Quarantine actions:** any BD user can add a work email, fix and release a row (release revalidates it); only the importer, a manager or an admin can discard (D-107). Discard is audited.
- **Source engagement history (D-073):** do-not-contact or unsubscribed becomes an opt-out; bounced marks the email invalid; replied excludes the person from new campaigns and flags the BD owner; contact within the cooling-off period (default 90 days) starts the cooling-off. The app's own send records win, otherwise the most recent date wins.
- **Ownership (D-075):** source-owner names map to app users by name; unmatched leads go to the Unassigned pool for a manager to assign.
- **Open:** the personal-email domain list and the generic-prefix list are `[UNRESOLVED]` (U3). `[SUGGESTION]` Make both admin-editable settings.

## 5. Matching and deduplication (module D)
- **Person match order:** source record ID, then normalized email, then LinkedIn URL, then name plus company domain (D-077).
- **Company match order:** Apollo Account ID, then domain (work email first, website as fallback), then normalized name.
- **Merge:** latest import wins per field; a blank incoming value never erases existing data. `[ASSUMPTION]` "Latest" means latest import time. The app's own send records win over source dates (D-073).
- **Uncertain matches:** name-plus-domain matches only produce a *possible* duplicate, never an automatic merge `[ASSUMPTION]`. They are imported as separate "Possible duplicate" records, excluded from campaigns until a manager or admin merges them or marks them "not a duplicate" (D-092). The "not a duplicate" decision is remembered.
- **Manual merge (D-108):** the most recent value per field is pre-selected and editable; all email addresses are kept; campaign history and timelines from both records are combined.
- **Change summary (D-050):** after each import, a one-time "what changed" view (transient, per import, not a permanent per-lead log).
- **Open:** confidence scoring is `[UNRESOLVED]`.

## 6. Import report
Shown after every import and downloadable (D-050): totals (received, imported, updated, unchanged, duplicates found, quarantined, rejected), a reason-coded breakdown of failures, and a list of the specific failed or quarantined rows. Quarantined-row and change-summary downloads are limited to the importer, managers and admins, and every download is audit-logged (D-111). CSV exports neutralise formula injection.

## 8. Job: `process_import`
A thin Procrastinate task wrapping the import service. Triggered when the upload is confirmed. Chunked and resumable, progress stored on `ImportFile`, per-row errors never fail the file, and a re-run after a worker crash is idempotent (no duplicate people, no double-counted totals). Duplicate-job prevention uses a queueing lock keyed on the import ID plus state checks in the service (plan §8, `[SUGGESTION]`).

## 10. Acceptance criteria
- Re-uploading the same file is flagged with the earlier date and user.
- A file with 10% bad rows still imports the other 90%.
- Every raw row is retrievable unchanged.
- A second import with changed data merges per latest-wins and produces a what-changed summary, with no permanent history.
- Possible duplicates reach the manager screen.
- A real Apollo, Excel or CSV file loads into clean People and Companies, with problems quarantined.

## 11. Tests
Each rule has an automated test, on real PostgreSQL with pgvector and synthetic data:
- each match path (source ID, email, LinkedIn URL, name plus domain; company ID, domain, name);
- merge precedence, blank values not erasing data, all emails kept, combined timelines, "not a duplicate" remembered;
- each quarantine reason; release revalidates; discard audited; permission checks for release, discard and download;
- duplicate file, missing headers, mixed valid and invalid rows, file size and row limits;
- large-file import and idempotent re-run after a worker crash;
- raw-data preservation (raw rows unchanged; only erase-person removes them);
- engagement-history rules (opt-out, bounced, replied, cooling-off).

## 12. Demo
Import sample files; show the preview and the mapping; show the quarantine list; fix and release one record; merge a duplicate; show the import report and the change summary.

## 13. Rules that apply to every milestone
ruff, tsc and ESLint clean; pytest and frontend tests green; Alembic migrations reviewed; OpenAPI schema and generated client in sync; audit events wired for new sensitive actions; no secrets in code; docs updated.

## 18. The seam between the workstreams (contract)

M2-0 creates `app/leads/contracts.py` (types and one function signature, no logic). This is the single integration point:

- **`SourceRow`** (W1 to W2): row number, the file's column values already mapped to app field names, the raw email text, `import_file_id`, source profile and default country.
- **`ImportContext`**: import file id, uploader, the "now" from `core.clock.now()`, cooling-off days, and a flag saying whether this call comes from an import or from a quarantine release.
- **`ingest_row(session, row: SourceRow, ctx: ImportContext) -> RowOutcome`**: owned and implemented by **W2** (`leads/ingest.py`). It normalizes, validates, quarantines, matches, merges or flags a possible duplicate, applies engagement-history rules, and writes the `ImportChange` row when an existing person changed. It never commits; the caller owns the transaction.
- **`RowOutcome`**: one of `imported`, `updated`, `unchanged`, `quarantined`, `possible_duplicate`, `rejected`, plus a reason code and the person id when there is one. **W1** only counts these into the `ImportReport`.
- **`ImportChange.changes` JSON shape** (W2 writes it, W1's report page reads it): a list of `{field, old, new}` objects. Defined in `contracts.py`.
- **Not duplicated:** W1 never validates, matches or merges; W2 never parses files or touches `ImportFile`. W2's quarantine "release" calls `ingest_row` again, so there is one pipeline for both paths.

Each side works against this contract alone. W1 tests `pipeline.py` with a fake `ingest_row`; W2 tests `ingest_row` and its parts directly on database rows built with factories. The real function is connected in `imports/wiring.py` at integration step I1 (section 21).

## 20. Rules that keep the two developers from conflicting

1. **One owner per file** (section 17). Need a change in a file you do not own? Ask the owner; never edit it yourself, even for one line.

## 24. Git workflow (exactly when to branch, commit, push and merge)

Developers run Git themselves; Claude Code does not commit, switch branches, push or merge. The integration branch is `main`; there is no long-lived M2 branch, so every PR targets `main`.

1. **Protect `main`** (repository setting `[SUGGESTION]`, as in M1): changes only by pull request, one approval from the other developer, `make check` green, squash merge, delete the branch after merge.
2. **Create the branch** only when every task in "Depends on" is merged: `git switch main && git pull --ff-only`, then `git switch -c m2/<a|b>-<n>-<slug>`. One task, one branch, one PR. Never reuse a branch.
3. **Start implementation** right after the branch exists. Tasks that need an approval (`openpyxl`, seed lists, a migration) start only after you approve. Any task with an endpoint writes the schemas, the permission and the generated client first, so the screen and the service agree on the shape before the logic is written.
4. **Commit** after every green step, with code, tests and screen changes that belong together in one commit, so each commit passes `ruff`, `pytest`, `tsc`, ESLint and Vitest. Message `type(scope): subject` (for example `feat(imports): add SHA-256 duplicate-file check`), ending with the co-author line when Claude helped. Never commit `.env`, secrets, `.claude/settings.local.json`, real lead data or uploaded files.
5. **Sync, then push:** `git fetch origin && git rebase origin/main` before the first push and again before opening the PR; rerun the checks after each rebase. Never `git merge main` into a feature branch. Push at the end of every working day and when the task is done: `git push -u origin <branch>` first, `git push` after, `git push --force-with-lease` only on your own branch after a rebase, never `--force`, never on `main` or the other developer's branch.
6. **Open the PR** when the task's acceptance items pass locally. The last commit regenerates `openapi.json` and the generated client if endpoints changed, and updates `filedescription.md`, `FILE_STRUCTURE.md`, `database.md`, `ARCHITECTURE.md` (where relevant), the `USERPROMPT.md` summary and your lines in section 23. State in the description which gate it clears or waits for.
7. **Review:** the other developer reviews. A PR that edits a file outside its workstream's list in section 17 is blocked.
8. **Merge** (squash) into `main` only when approved and green. Both developers then run `git switch main && git pull --ff-only` before the next task. When a PR that changes an endpoint merges, the other developer regenerates the client at the start of their next branch.
9. **Merge order when dependencies exist:** see section 21. In short: G2, M2-0, then independent task streams; M2-A7 last.

### A0: Scaffold (M2-0)

**M2-0: Contracts and scaffold** (branch `m2/a-0-scaffold`, depends on: the M1 A6 to A11 branch merged)
- **Purpose:** Prepare the shared parts of the project once, so that afterwards the two developers never edit the same file.
- **Builds:** An agreement file (`leads/contracts.py`) describing how the two workstreams talk to each other, empty placeholders for the new pages and API routes, the menu links, and the list of audit actions M2 will need.
- **How it works:** It contains no real logic, only empty shells and names. Both developers then fill in different shells, in different folders.
- **Needed:** First, because everything else builds on it. It is small (about a day), and the other developer reviews it before it is merged.

### Developer A: Intake and processing

**M2-A1: Upload and duplicate-file check** (branch `m2/a-1-upload`, depends on: M2-0)
- **Purpose:** Let a user bring a spreadsheet into the app safely, and warn them if the same file was already uploaded.
- **Builds:** The code that reads CSV and Excel files, an upload API, and an upload page with a warning message and a worksheet picker.
- **How it works:** The server checks the file size and row count, creates a digital fingerprint of the file (SHA-256), and compares it with earlier uploads. If it matches, the page shows who uploaded it and when, and asks "cancel or import anyway".
- **Needed:** Every import starts here. It also stops accidental double uploads. Adding the Excel-reading library (`openpyxl`) needs your approval first.

**M2-A2: Mapping, preview and estimate** (branch `m2/a-2-mapping`, depends on: M2-A1)
- **Purpose:** Tell the app which spreadsheet column means what (for example, "E-mail Address" is the email), and show what will happen before anything is saved.
- **Builds:** The mapping API and the wizard steps: choose a source profile and default country, map the columns, fix missing headers, preview the first rows, see an estimate, then start the import.
- **How it works:** The server suggests a mapping (for Apollo files it already knows the layout), the user adjusts it, and the choice can be saved to reuse for the next file.
- **Needed:** After upload and before the import runs, so the import reads the right data. It saves time on repeat imports.

**M2-A3: Import pipeline and background job** (branch `m2/a-3-pipeline`, depends on: M2-A2)
- **Purpose:** Run the actual import in the background without freezing the page, and never fail the whole file because of a few bad rows.
- **Builds:** The `process_import` job, the loop that handles the file in chunks, the progress counters, and the matching of "owner" names in the file to app users.
- **How it works:** For each row it first saves the original (raw row), then hands the row to one function, `ingest_row`, built by Developer B, and counts the answer. Tests use a fake `ingest_row`, so this task does not wait for B.
- **Needed:** After mapping. If the worker stops halfway, running the job again must give the same result with no duplicates, and the tests prove it.

**M2-A4: Progress page and owner assignment** (branch `m2/a-4-progress-ui`, depends on: M2-A3)
- **Purpose:** Show the user how far a running import is, and let a manager assign leads whose owner could not be found.
- **Builds:** A progress page that updates by itself, and a small screen listing "Unassigned" leads with an assign action and its audit record.
- **How it works:** The page asks the server every few seconds for the counters stored by the job. The assignment screen changes a lead's owner, which only managers and admins may do.
- **Needed:** After the job exists, so users can see what is happening during large imports. Unassigned leads would otherwise stay without an owner.

**M2-A5: Import report, change summary and downloads** (branch `m2/a-5-report`, depends on: M2-A3)
- **Purpose:** Show what an import did, and let the right people download the problem rows.
- **Builds:** The report API and page (totals, reasons for failures, a "what changed" list for updated leads) and CSV downloads of failed and quarantined rows.

## 29. Working habits that prevent conflicts `[SUGGESTION]`

| Habit | Why it is useful, in simple words |
|---|---|
| One task, one branch, one Claude session. Start a fresh session (`/clear`) for each task | Claude does not carry old assumptions into a new task, and each PR contains only that task. |
| Begin each task by telling Claude the task ID and its "Depends on" list, and ask it to read the relevant files first | It works from what exists, not from a guess. |
| Say "propose first" for anything with an approval (`openpyxl`, seed lists, a migration) | Matches the project rule: no new tool or dependency without your yes. |
| Read every edit prompt; approve one at a time; never choose "always allow" for edits | You see exactly what changes. A big surprise is caught before it is written. |
| Run `git status` and `git diff` before every commit; a file outside your workstream list in section 17 means stop | That is how an accidental overlap is caught before the other developer sees it. |
| Pull `main` and regenerate `openapi.json` or the client after the other person's PR merges | Generated files are rebuilt, not merged by hand, so they never hold stale or mixed content. |
| Do not ask Claude to run Git commands | Branching, committing, rebasing, pushing and merging are done by the developer (section 24). |
| Keep each Claude session on one workstream's folders; use a separate working copy (a second clone or `git worktree`) if you must look at the other branch | You cannot overwrite your own files with the other branch's versions by switching branches under Claude. |
| Put secrets only in `.env` files, which Claude cannot read; use synthetic lead data in tests and fixtures | Keeps real data and passwords out of conversations, logs and Git. |
