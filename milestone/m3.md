# M3: Lead search, lead details, eligibility, opt-outs, exports

Source: `docs/plan.md` §16 (M3), with detail from §6.2 (entities), §7 (module APIs), §9 (AI integration, NL search), §11.2 (limits), §14 modules E, F and G, §15 (dependencies) and §17 (open items U1, U4, U5, U7, U14, U18), and decisions D-009 to D-011, D-022, D-024 to D-027, D-060 to D-067, D-073, D-075, D-079, D-080, D-085, D-087, D-092, D-098, D-099, D-101, D-106 in `docs/requirements/Q-A.md`. Nothing here is new scope. Status: **planned, not started**.

## 1. Purpose and output
M2 fills the lead tables. M3 lets people use them: reps and managers find leads, open a lead or company page, see why a lead can or cannot be contacted, record and remove opt-outs, assign owners, flag leads, save segments and export results. It delivers:
- structured search from one filter definition (`FilterSet`), with pagination, selection and "select all matching",
- saved segments, private by default,
- lead and company detail pages with timeline, emails, notes, flags and contact history,
- one eligibility service whose bulk (SQL) and per-record versions are proven to agree,
- opt-outs (manual, imported, reply), the Opt-outs page and the admin-only "Erase person",
- assignment of owners and the Unassigned pool, and CSV export with audit,
- natural-language (NL) search through a minimal Gemini adapter, the first AI integration.

It does not include campaigns, drafting or sending (M4 onward), reply handling (M6) or the real-sending gate (M8). Reps can find and export eligible leads; nothing is sent.

## 2. Tasks

| # | Task | What it means |
|---|---|---|
| 1 | `FilterSet` and structured search | One filter definition used by the form, saved segments and AI output. The query is built only from it; unsupported fields are rejected. |
| 2 | Pagination and selection | Select single leads or "all matching"; "all matching" stores the **filter**, resolved at campaign time, so counts are never stale. |
| 3 | Saved segments | Name and save a filter set; private by default, optionally shared with the team (D-098). |
| 4 | Lead and company detail pages | Timeline, all emails, notes, status, flags, contact history, opt-out banner. |
| 5 | Notes | Any BD user adds notes to a lead (colleague activity notes). |
| 6 | Eligibility service with a parity-tested bulk query | Each rule is written once as a pair (SQL expression, record check); a test compares both on generated data. |
| 7 | Opt-outs | Manual, imported and reply opt-outs; any BD user adds; manager or admin removes with a reason; searchable Opt-outs page. |
| 8 | Erase person | Admin only; removes the person's data, keeps the address on the opt-out list (D-099). |
| 9 | CSV export with audit | Search results, within what the caller can see; every export logged (D-087). |
| 10 | NL search with a Gemini adapter | A sentence becomes filters; the user sees and edits them before anything runs. |
| 11 | Assignment and the Unassigned pool | Manager or admin assigns owners singly or in bulk (D-075). |
| 12 | Status flags, contact history, same-account note | Qualified, Handed Off, existing customer, in conversation, partner, competitor (D-065, D-101); history visible to all reps (D-026); note when a colleague engages the same company (D-027). |

## 3. Data model scope
No new tables are expected: the models and migrations already exist from M1 (`0006` leads, `0008` compliance). M3 adds services, APIs and screens on top of them. Any schema change M3 needs (for example search indexes) is a new migration, never an edit of an applied one, and updates `database.md`.

- **leads:** `Person`, `Company`, `PersonEmail`, `PersonPhone`, `SocialProfile`, `ContactChannel`, `Segment` (name, filters JSON, private or shared, owner), `LeadNote`, `LeadEvent` (timeline), `Touch` (contact history), `LeadStatusFlag`, `DuplicateCandidate` (possible duplicate = an open candidate, D-092), plus the engagement fields on `Person` written by M2 (`last_contacted_at`, `email_bounced`, `replied_at`, owner).
- **compliance:** `OptOut` (per normalized address; source manual, imported or reply; created_by; removed_at, removed_by, removal_reason), `ErasureRecord` (former person id and counts only, no personal data). `EligibilitySnapshot` stays unbuilt (no requirement needs it).
- **core:** `Setting` (cooling-off days, AI model names).
- **audit:** opt-out add and removal, flag changes, assignment, note, segment, export, erase and NL-search events are audited.

Modeling rules that apply:
- Unified data keeps the latest values only (D-008). Possible duplicate is derived from open `DuplicateCandidate` rows, never stored on the person.
- Opt-outs are the only enforced suppression (D-065, D-066): stored per email address, so they cover addresses without a person and survive erase-person. `[AGREED]`
- Contact details never go to the AI (plan §9). `[AGREED]`

## 4. Eligibility and compliance rules (module G)
- **One service, no bypass:** `check_eligibility(person, context)` returns reason codes. Search uses it now; campaign creation, drafting and sending (M4 onward) call the same service. `[AGREED]`
- **Not eligible when:**
  - `opted_out`: an active opt-out exists for the address (D-066; no BD override; re-checked before sending, D-011).
  - `no_usable_email`: no work email that is not marked invalid (bounced, D-073; D-072: personal, generic and secondary addresses are never used).
  - `replied`: the person replied (D-082).
  - `cooling_off`: last contact is inside the cooling-off period (default 90 days, `Setting` key `campaigns.cooling_off_days`, D-073, D-083).
  - `contact_limit`: more than 3 emails in 30 days `[ASSUMPTION]` counted from `touches` until M5 creates outgoing rows (open decision 2).
  - `possible_duplicate`: an open duplicate pair involves the person (D-092).
  - `qualified_or_handed_off`: set by a BD user (D-101).
- **Warnings that do not block:** unverified email (D-042). Status flags such as existing customer, partner or competitor do not block either: there is no separate suppression list (D-065).
- **Parity (technical risk):** search needs a bulk SQL version and sending a per-record version, and they can drift. Each rule is one pair (SQL expression plus record check) and a parity test compares both over generated data. `[SUGGESTION]` from plan §14 G.
- **Opt-outs:** any BD user can add one; only a manager or admin can remove one, with a recorded reason, audited (D-066). Opt-outs written by M2 (do-not-contact) appear here.
- **Erase person (D-099):** admin only; removes the person's details, emails, phones, original imported rows and stored replies; keeps the address on the opt-out list so future imports never revive it; writes an `ErasureRecord` with counts only; audited.
- **Open:** retention periods for other data are `[UNRESOLVED]` (U18).

## 5. Search rules (module F)
- **One `FilterSet` definition** used by the form, saved segments and AI output; the query is built only from it. Unsupported fields are rejected. `[AGREED]`
- **Filters:** industry, company size (bands SMB 1 to 200, mid-market 201 to 1,000, enterprise above 1,000, D-085), location, job title, tech stack, revenue, funding stage, Salesforce usage (D-025).
- **Default view:** every lead except opted-out ones, with badges for cooling-off, replied, possible duplicate, unverified email and opted out. "Eligible only" is a filter, off by default; "Show opted-out" reveals them (D-106, D-067).
- **Selection:** "select all matching" stores the *filter*, with the lead set resolved at campaign time. `[SUGGESTION]`
- **Visibility:** every rep sees every lead and its contact history (D-001, D-026); a note shows when a colleague already engages the same company (D-027).
- **Open:** whether text search on names and titles needs a new index (a migration, needs approval).

## 6. Opt-out page, export and AI search
- **Opt-outs page (D-067):** searchable by address, date, reason and source; "Opted out" badge in search, banner on the lead page.
- **CSV export (D-087):** for search results, all roles, within what the caller can already see; every export is audit-logged; formula injection is neutralised.
- **NL search (plan §9):** the AI receives only the typed sentence and the list of supported filter fields and allowed values, and returns filter JSON. Unknown fields are dropped and reported. It cannot produce SQL. The user sees and edits the interpreted filters before the search runs. If the AI is unavailable, structured search still works. Model name comes from settings, logs never hold prompts with lead data. The `ai-adapter` skill must be loaded before any AI work.

## 7. Modules touched
- **E. Lead and company management:** the screens (lead detail, company detail, notes, flags, assignment) that M1 only modelled.
- **F. Lead search:** the whole module.
- **G. Eligibility and compliance:** eligibility, opt-outs, erase-person (the real-sending gate is M8).
- **AI (new, minimal):** `ai/` adapter, Gemini and fake providers, NL search only.

- Skills to load: `outreach-compliance` for every compliance task, `ai-adapter` for the AI task.

## 8. Jobs

## 10. Acceptance criteria
- An NL query shows editable filters before running; invented fields never reach the query.
- Opted-out leads never show as eligible.
- Removing an opt-out needs a reason and is audited.
- The bulk (SQL) and per-record eligibility agree on generated data.
- "Select all matching" stores the filter, not a list.
- Exports respect permissions and are audited; formula injection is neutralised.
- Erase removes the person's data everywhere but keeps the opt-out address.
- Reps can find and export eligible leads.

## 11. Tests
Each rule has an automated test, on real PostgreSQL with pgvector and synthetic data:
- every eligibility reason code, warnings that do not block, and **search/eligibility parity**;
- each filter alone and combined, default view, "eligible only", "show opted-out", pagination;
- select-all semantics, saved segments (private and shared), export permissions and audit;
- NL parser rejects invented fields; adversarial inputs (prompt-injection style text in the query); AI outage leaves structured search working (fake provider);
- opt-out removal needs a reason; any BD user may add; imported opt-outs show on the page;
- erase removes raw rows, emails, phones and replies and keeps the opt-out; erase is admin-only and audited;
- assignment, flags and notes: permissions, audit, timeline entries;
- permission matrix rows for every new endpoint.

## 12. Demo
Run a structured search; run the CFO / pharma / Karnataka NL query; adjust the interpreted filters; save a segment; open a lead (opt-out banner on an opted-out lead); assign owners; flag a lead; export; erase a test person.

## 13. Rules that apply to every milestone
ruff, tsc and ESLint clean; pytest and frontend tests green; Alembic migrations reviewed; OpenAPI schema and generated client in sync; audit events wired for new sensitive actions; no secrets in code; docs updated.

## 18. The seam between the workstreams (contract)

M3 has **no shared function**. The two lanes agree on three small things in M3-0, all of them names, not logic:

- **Tables as the contract.** Who writes and who reads each table is fixed, so neither lane calls the other's code:

| Table | Written by | Read by |
|---|---|---|
| `opt_outs` | W2 (opt-out service); also M2's engagement rules | W1 eligibility and badges |
| `lead_status_flags` | W2 (flag service) | W1 eligibility (Qualified, Handed Off) and badges |

| `segments` | W1 | W1 |
| `erasure_records` and deletions across person tables | W2 (erase) | nobody |

- **URL paths.** M3-0 fixes the routes both lanes link to: `/leads` (search), `/leads/{personId}` (lead page), `/companies/{companyId}`, `/opt-outs`, `/leads/unassigned`. - **Not duplicated:** W1 never writes opt-outs, flags, notes or owners; W2 never builds filters, search queries or eligibility rules.

Each side works against this alone. W1 tests search and eligibility on rows built with factories; W2 tests records, opt-outs and erase on rows built with factories. M2's data is used only through the tables.

## 20. Rules that keep the two developers from conflicting

1. **One owner per file** (section 17). Need a change in a file you do not own? Ask the owner; never edit it yourself, even for one line.
2. **Pre-wired shared files.** M3-0 does the only edits to `main.py`, `audit/services.py`, `permissions.py` and `nav-items.ts`. After that, a feature PR adds only new files and edits only files under its own workstream in section 17.
3. **No code calls across lanes.** W1 reaches W2 only through the tables and URL paths in section 18; W2 reaches W1 only the same way (and, in M3-B7, through W1's merged eligibility service). `test_m3_lane_isolation.py` fails if a W1 file imports a W2 module or the other way round. Changing section 18 needs both developers' approval.
4. **Migrations.** M3 is planned with **no new tables and no migration**. If one becomes unavoidable (for example search indexes), the workstream owner proposes it first, numbers it after the current head with `down_revision` set to that head, and never edits an applied migration. The single-head test fails any fork.
5. **`openapi.json` and the generated client are regenerated, never merged by hand.** After a rebase conflict in `BD_BACKEND/openapi.json` run `python -m app.export_openapi`; in `BD_FRONTEND/src/lib/api/**` run `npm run generate:api`. Every PR that changes an endpoint includes both regenerated files, and each developer's frontend code uses only the generated client.
6. **`USERPROMPT.md` and shared docs.** Both append; on a conflict keep both sides and renumber only your own newest entry. Check the last ID with `grep -n "^## T-" USERPROMPT.md | tail` right before appending. In `filedescription.md`, `FILE_STRUCTURE.md`, `database.md` and this file, each developer edits only their own rows and status lines, in the last commit, after rebasing.
7. **No shared UI components.** Each workstream builds its tables and dialogs inside its own `components/<search|lead|optouts>/` folder. A genuinely shared component is requested from the other developer, never copied into their folder.
8. **Branch from `main` only.** A branch is created only after everything it depends on is merged, so nobody builds on an unmerged branch of the other developer.
9. **Test data does not collide.** W1 builds its search data in the new `tests/factories/search.py`; W2 extends `factories/leads.py` and `factories/compliance.py`. Neither edits the other's file.

## 24. Git workflow (exactly when to branch, commit, push and merge)

Developers run Git themselves; Claude Code does not commit, switch branches, push or merge. The integration branch is `main`; there is no long-lived M3 branch, so every PR targets `main`.

1. **Protect `main`** (repository setting `[SUGGESTION]`, as in M1 and M2): changes only by pull request, one approval from the other developer, `make check` green, squash merge, delete the branch after merge.
2. **Create the branch** only when every task in "Depends on" is merged: `git switch main && git pull --ff-only`, then `git switch -c m3/<a|b>-<n>-<slug>`. One task, one branch, one PR. Never reuse a branch.
3. **Start implementation** right after the branch exists. Tasks that need an approval (the Gemini library, a migration) start only after you approve. Any task with an endpoint writes the schemas, the permission and the generated client first, so the screen and the service agree on the shape before the logic is written.
4. **Commit** after every green step, with code, tests and screen changes that belong together in one commit, so each commit passes `ruff`, `pytest`, `tsc`, ESLint and Vitest. Message `type(scope): subject` (for example `feat(compliance): add the opt-out service`), ending with the co-author line when Claude helped. Never commit `.env`, secrets, `.claude/settings.local.json`, real lead data or API keys.
5. **Sync, then push:** `git fetch origin && git rebase origin/main` before the first push and again before opening the PR; rerun the checks after each rebase. Never `git merge main` into a feature branch. Push at the end of every working day and when the task is done: `git push -u origin <branch>` first, `git push` after, `git push --force-with-lease` only on your own branch after a rebase, never `--force`, never on `main` or the other developer's branch.
6. **Open the PR** when the task's acceptance items pass locally. The last commit regenerates `openapi.json` and the generated client if endpoints changed, and updates `filedescription.md`, `FILE_STRUCTURE.md`, `database.md`, `ARCHITECTURE.md` (where relevant), the `USERPROMPT.md` summary and your lines in section 23. State in the description which gate it clears or waits for.
7. **Review:** the other developer reviews. A PR that edits a file outside its workstream's list in section 17 is blocked.
8. **Merge** (squash) into `main` only when approved and green. Both developers then run `git switch main && git pull --ff-only` before the next task. When a PR that changes an endpoint merges, the other developer regenerates the client at the start of their next branch.
9. **Merge order when dependencies exist:** see section 21. In short: G1, M3-0, then two independent task streams; M3-B7 last.

## 27. Plain-language task guide

**How to read this.** Task IDs in the request map to section 19 like this: **B0 = M3-0**, **A1 to A6 = M3-A1 to M3-A6**, **B1 to B7 = M3-B1 to M3-B7**. Status for every task is "Pending" today (see section 23).

### Words you will meet

| Word | Meaning in this project |
|---|---|
| Lead | A person (a possible customer) and the company they work for, stored as a `Person` and a `Company`. |
| Filter | One condition for a search, such as "industry is pharma". A set of them is a `FilterSet`. |
| Segment | A saved filter set with a name, private to its owner or shared with the team. |
| Eligible | A lead the app may contact. A lead is not eligible if it opted out, replied, was contacted recently, has no usable email, and so on. |
| Opt-out | A record that an email address must never be contacted. It is the only suppression the app enforces. |
| Cooling-off | A waiting period (default 90 days) after contacting someone before a new campaign may target them. |
| Parity test | A test that proves two versions of the same rule (database query and single-record check) give the same answer. |
| Erase person | An admin action that removes a person's data everywhere but keeps their address on the opt-out list. |
| AI adapter | One piece of code between the app and the AI provider, so the provider can be changed without touching anything else. |
| Contract | A written agreement about what one piece of code gives to another, so two people can build each side separately. |
| Fake (test double) | A stand-in used in tests so you do not need the real service (for example the AI) yet. |
| Migration | A script that changes the database structure. M3 plans none. |

### B0: Scaffold (M3-0)

**M3-0: Names and scaffold** (branch `m3/b-0-scaffold`, depends on: M2 merged to `main`)
- **Purpose:** Prepare the shared parts of the project once, so that afterwards the two developers never edit the same file.
- **Builds:** Empty placeholders for the new pages and API routes, the menu links, the list of audit actions M3 needs, three new permissions, and a test that stops one lane from importing the other's code.
- **How it works:** It contains no real logic, only empty shells and names. Both developers then fill in different shells, in different folders.
- **Needed:** First, because everything else builds on it. It is small (about a day), and the other developer reviews it before it is merged.

### Developer A: Find and select leads

**M3-A1: Eligibility service** (branch `m3/a-1-eligibility`, depends on: M3-0)
- **Purpose:** Give the whole app one answer to "may we contact this person, and if not, why not?".
- **Builds:** The rules (opted out, no usable email, replied, cooling-off, contact limit, possible duplicate, Qualified or Handed Off), each in a database version and a single-record version, plus the test that proves they agree.
- **How it works:** Each rule is written once as a pair. Search uses the database version for thousands of leads at once; sending will use the single-record version before every email. The parity test runs both on generated data.
- **Needed:** Before search, because search shows eligibility badges and an "eligible only" filter. It is also the base for campaigns and sending in later milestones.

**M3-A2: Filters and search backend** (branch `m3/a-2-search-backend`, depends on: M3-A1)
- **Purpose:** Let people find leads by industry, size, place, title, technology, revenue, funding stage and Salesforce use.
- **Builds:** The one filter definition, the search service, the endpoint, paging and sorting, badges, and the "eligible only" and "show opted-out" options.
- **How it works:** The server builds the query only from the filter definition, so an unsupported field is refused. By default everyone except opted-out leads is shown, each with badges.
- **Needed:** The core of replacing Apollo's search. The screen, saved segments, export and NL search all build on it.

**M3-A3: Search screen and selection** (branch `m3/a-3-search-screen`, depends on: M3-A2)
- **Purpose:** Give reps a page to filter, browse and pick leads.
- **Builds:** The filter panel, chips for the active filters, the results list with badges and pages, select one or "select all matching".
- **How it works:** "Select all matching" remembers the filter, not the list of leads, so the count is always current when a campaign is made later. Each result links to the lead page.
- **Needed:** After the search backend. The "add to campaign" button stays disabled until M4.

**M3-A4: Saved segments** (branch `m3/a-4-segments`, depends on: M3-A2)
- **Purpose:** Let people reuse a filter combination.
- **Builds:** Save, list, rename, delete and share a segment, with a panel on the search page.
- **How it works:** A segment is private to its owner unless shared with the team; only the owner changes or deletes it. Each change is audited.
- **Needed:** After the filters exist. It saves time on repeat searches.

**M3-A5: CSV export** (branch `m3/a-5-export`, depends on: M3-A2)
- **Purpose:** Let people download search results, as Apollo did.
- **Builds:** An export of the current filter's results and a download button.
- **How it works:** It exports only what the caller may already see, makes the file safe against spreadsheet "formula tricks", and logs who exported what filter and how many rows (never the rows themselves).
- **Needed:** After search. Every export is accountable.

**M3-A6: AI adapter and natural-language search** (branch `m3/a-6-nl-search`, depends on: M3-A2; needs the Gemini approval)
- **Purpose:** Let someone type "CFOs at pharma companies in Karnataka" instead of picking filters.
- **Builds:** The AI adapter, the Gemini and fake providers, the sentence-to-filters step, and the box on the search page that shows the filters for editing.
- **How it works:** Only the sentence and the list of allowed filter fields go to the AI. It returns filters; any field it invents is dropped and reported. The user sees and edits the filters before the search runs. If the AI is down, normal search still works.
- **Needed:** Last in this lane, because it needs your approval of the library and key. It is the first AI use in the app.

### Developer B: Lead records and compliance actions

**M3-B1: Opt-outs** (branch `m3/b-1-opt-outs`, depends on: M3-0)
- **Purpose:** Keep a reliable list of addresses that must never be contacted.
- **Builds:** The opt-out service, its API and the Opt-outs page: add, search, and remove with a reason.
- **How it works:** Anyone can add an opt-out; only a manager or admin can remove one, and must give a reason. Removal keeps a record rather than deleting. Every change is audited.

**M3-B2: Status flags** (branch `m3/b-2-flags`, depends on: M3-0)

- **How it works:** Any BD user can set or clear a flag; each change records who and when, adds a timeline entry and an audit record. Qualified and Handed Off make a lead ineligible for campaigns.

**M3-B3: Assignment and Unassigned pool** (branch `m3/b-3-assignment`, depends on: M3-0)

- **Builds:** The assignment service and a screen listing unassigned leads with single and bulk assign.

**M3-B4: Notes, contact history and same-account note** (branch `m3/b-4-notes-history`, depends on: M3-0)

## 29. Working habits that prevent conflicts `[SUGGESTION]`

| Habit | Why it is useful, in simple words |
|---|---|
| One task, one branch, one Claude session. Start a fresh session (`/clear`) for each task | Claude does not carry old assumptions into a new task, and each PR contains only that task. |
| Begin each task by telling Claude the task ID and its "Depends on" list, and ask it to read the relevant files first | It works from what exists, not from a guess. |
| Say "propose first" for anything with an approval (the Gemini library, a migration) | Matches the project rule: no new tool or dependency without your yes. |
| Load the `outreach-compliance` skill for compliance tasks and the `ai-adapter` skill for the AI task | Both areas have rules that are easy to get wrong without them. |
| Read every edit prompt; approve one at a time; never choose "always allow" for edits | You see exactly what changes. |
| Run `git status` and `git diff` before every commit; a file outside your lane in section 17 means stop | That is how an accidental overlap is caught before the other developer sees it. |
| Pull `main` and regenerate `openapi.json` or the client after the other person's PR merges | Generated files are rebuilt, not merged by hand. |
| Do not ask Claude to run Git commands | Branching, committing, rebasing, pushing and merging are done by the developer (section 24). |
| Never put the Gemini key, real prospect data or secrets in a prompt, a fixture or a commit | Keys live only in `.env` files, which Claude cannot read; fixtures are synthetic. |
