# M1: Project setup and data model

Source: `docs/plan.md` §16 (M1), with detail from §6.2 (entities), §6.3 (modeling decisions), §14 (modules A, E, S, T) and §15 (dependencies). Nothing here is new scope. Anything not yet built is "planned".

## 1. Purpose and output
M1 lays the foundation every later milestone builds on. It delivers:
- a running app (backend + frontend skeleton) with working login,
- empty shells for the screens that later milestones fill in,
- the full initial database schema for all modules, reviewed with the business owner.

It contains no business features such as import, search or sending.

## 2. Tasks

| # | Task | What it means |
|---|---|---|
| 1 | Backend skeleton | FastAPI app, settings (`config.py`, fail-fast on missing env vars), SQLAlchemy 2.x and Alembic. |
| 2 | Frontend skeleton | Next.js + TypeScript, with the API client generated from the backend's OpenAPI schema (never hand-edited). |
| 3 | `.env` handling | Environment-variable configuration for both backend and frontend; real `.env` files stay out of git. |
| 4 | Database | PostgreSQL 17 with the pgvector extension, set up on Mac (Docker Compose is also in scope for local dev, decision 0001). |
| 5 | Procrastinate | Job queue with a no-op worker, proving that background jobs run. |
| 6 | Users and auth | `User` with roles, session login, and permission dependencies enforced server-side. |
| 7 | `core.clock` | The single source of time, `now()`, with an admin test offset. Code never calls `datetime.now()`. |
| 8 | Audit module (basic) | Append-only audit log and a `record()` service. Other modules may call it. |
| 9 | Full initial data model | Models and migrations for all modules (see §3). Admin screens follow in M5. |
| 10 | Base layout and login page | Next.js shell and a login page. |
| 11 | Test scaffolding | pytest with factories; Vitest and Playwright set up. |
| 12 | `make check` | One command that runs ruff, pytest, tsc, ESLint and the frontend tests. |

## 3. Data model scope
Models and migrations are created for every app now, even though most screens come later. Key fields only (the full field list is settled in M1):

- **core:** `User` (role, active), `Setting` (key, typed value, version), `ClockOffset`, `JobLock`.
- **imports:** `ImportFile`, `SourceProfile` (three layouts still `[UNRESOLVED]`), `ColumnMapping`, `RawRow` (immutable original values, D-099), `ImportReport`.
- **leads:** `Company`, `Person`, `PersonEmail`, `PersonPhone`, `SocialProfile`, `ContactChannel`, `QuarantineRecord`, `DuplicateCandidate`, `MergeRecord`, `Segment`, `LeadNote`, `LeadEvent`, `Touch`, `LeadStatusFlag`, `IndustryMapping`, `StateMapping`.
- **compliance:** `OptOut` (per email address, D-066), `EligibilitySnapshot` (optional), `ComplianceGateStatus` / `ComplianceChecklistItem` (D-081), `ErasureRecord`.
- **content:** `VoiceSetting`, `SizeProfile`, `IndustryProfile`, `KnowledgeItem`, `KnowledgeEmbedding`, `EmailStructure` + `StructureSection`, `ConfigVersion`.
- **campaigns:** `Campaign`, `CampaignLead`, `EmailSequence`, `EmailDraft`, `ValidationResult`.
- **outreach:** `OutreachMessage` (the persistent send queue), `SendAttempt`, `Mailbox`.
- **mail:** `MailThread`, `OutboxMessage`, `InboundMessage`, `DeltaCursor`, `ReplyClassification`, `BounceRecord`.
- **notifications:** `Notification`, `SlaReminder`.
- **audit:** `AuditLog` (append-only).

Modeling decisions that apply (§6.3):
- Two data layers: `RawRow` is immutable; unified `Person`/`Company` keep the latest values only (D-008). `[AGREED]`
- Email addresses live in their own table (several per person, verification differs). `[AGREED]`
- Soft state instead of hard deletes, except the erase-person flow. `[SUGGESTION]`
- Voice, profiles and structures are versioned through `ConfigVersion` snapshots. `[AGREED]`
- The vector column is sized to the configured Gemini embedding model; model name and dimension are stored with each vector so a model change forces re-embedding. `[SUGGESTION]`

## 4. Modules touched
- **A. Authentication and user management:** backend and model in M1. Screens: login, logout, and (admin) user list and edit, "my profile". Server-side enforcement everywhere; owner-only draft editing; managers read-only.
- **E. Lead and company management:** data model only. Screens arrive in M3.
- **S. Audit and history:** built from M1 and extended each milestone. Audited actions include approval, export, merge, opt-out removal, erasure, settings changes and real-sending activation; role changes, login failures and import deletion are suggested. `[SUGGESTION]`
- **T. Admin settings:** some settings exist earlier (settings store); admin screens come in M5.

Cross-cutting pieces M1 provides to everything else: audit, permissions, test-clock `now()`, settings store.

**A8: CSRF, Origin and CORS** (branch `m1/a-csrf-cors`, no migration)
- Status: **Implemented 2026-11-24; PR pending review.** Verified in Docker: ruff clean, 499 tests pass; `openapi.json` regenerated.
- Design agreed before implementation (2026-11-24): the token is `sha256("csrf:" + raw session token)`, returned by login and `/auth/me` and compared in constant time; a present `Origin` must equal `FRONTEND_ORIGIN` exactly (login included) and a missing one falls through to the token check; `X-CSRF-Token` is required on POST, PUT, PATCH and DELETE except `POST /auth/login`; rejected requests are not audited; CORS allows exactly `FRONTEND_ORIGIN` with credentials and explicit methods and headers; no new dependency, table or column. Choices made while implementing, to confirm in review: the Origin check applies only to the state-changing methods (reads are governed by CORS); a request with no session cookie has no token, so an anonymous POST (even logout) is 403, not 401; the check is an app-level dependency, so it runs before route guards and before body validation; `CORSMiddleware` is built from `FRONTEND_ORIGIN` at import, so `app.main` needs `DATABASE_URL` when imported.
- Purpose: protect cookie sessions from cross-site requests (`ARCHITECTURE.md` section 4).
- Builds: an anti-CSRF header check on state-changing requests, an Origin check, CORS limited to the frontend origin (`FRONTEND_ORIGIN`, already in `config.py`), and the written contract in section 16 (header name, how the client obtains the token). Code in `app/core/csrf.py` and `app/main.py`.
- Use case: B's client sends the header on every POST/PUT/DELETE (task B12); requests without it are rejected and tested.
- Depends on: A0. Must merge before B12.

**A9: Login throttling** (branch `m1/a-login-throttle`, no migration unless approved)
- Status: **Implemented 2026-11-24; PR pending review.** Verified in Docker: ruff check clean, 515 tests pass; `openapi.json` unchanged (still 401).
- Design agreed before implementation (2026-11-24): failures are counted from existing `auth.login_failed` audit rows (no table, no migration, no dependency); 5 failures per account and 20 per client address in a rolling 15 minutes, configurable (`LOGIN_MAX_FAILURES_PER_ACCOUNT`, `LOGIN_MAX_FAILURES_PER_IP`, `LOGIN_THROTTLE_WINDOW_MINUTES`); a blocked attempt, even with the correct password, gets the same 401 as a wrong password; the account count only includes failures after the user's latest `auth.login_succeeded`, the address count is a strict rolling window; an unknown email is limited by address only; blocked attempts are audited as `auth.login_throttled` and never counted; the address stays `request.client.host` until deployment. Interpretations made while implementing, to confirm in review: `auth.login_succeeded` did not exist, so it was added to `AuditAction` and `login()` now writes one audit row per successful login; "per account for unknown emails" was read as address-only, as the approval states; inactive-user failures count like any other `auth.login_failed`; code in `app/core/login_throttle.py`, tests in `tests/test_login_throttle.py`.
- Purpose: slow down password guessing.
- Builds: a limit on failed logins per account and per client address, using the existing `auth.login_failed` audit rows (a small new table only if you approve it, and no new dependency), a uniform error response, and tests with the test clock.
- Use case: repeated failures are blocked and audited, while the response for an unknown email stays identical to a wrong password (no account discovery).
- Depends on: A8 (shares `config.py` and `core/api.py`, same developer, so sequential).

**API contract:** B generates its client only from `BD_BACKEND/openapi.json`. Today that is `/health`, `/auth/login`, `/auth/logout`, `/auth/me`. Endpoints from A7 and the CSRF changes from A8 (the `csrf_token` field on login and `/auth/me`, the CSRF `403` on every state-changing operation) are in the regenerated file; B regenerates the client afterwards (B2 script). The CSRF header itself is not an OpenAPI parameter; it is described in the contract above.

**CSRF, Origin and CORS contract (A8; B12 builds on this):**
- **Token.** `POST /auth/login` and `GET /auth/me` return the signed-in user plus `csrf_token` (`SessionUserResponse` in `openapi.json`). The token is `sha256("csrf:" + session token)` as hex, so it belongs to one session: a new login gives a new token and logout ends it.
- **Client duty.** Keep the token in memory only (not in `localStorage`, not in a cookie). After a full page reload, call `GET /auth/me` to get it again. Send it as the header `X-CSRF-Token` on every `POST`, `PUT`, `PATCH` and `DELETE`, including `POST /auth/logout`. The one exception is `POST /auth/login`: nobody has a token yet, so send none. `GET`, `HEAD` and `OPTIONS` need no header. Put this in the API client wrapper (`src/lib/api-client.ts`), never in the generated code, and keep sending `credentials: "include"`.
- **Origin.** The backend compares the browser's `Origin` header with `FRONTEND_ORIGIN` exactly (scheme, host and port; no trailing slash), also on login. Browsers set it themselves; the frontend must be served from exactly that origin, so `FRONTEND_ORIGIN` must match the address in the browser bar (for example `http://localhost:3000`, not `http://127.0.0.1:3000`).
- **Failure.** Any CSRF or Origin failure is `403` with the body `{"detail": "CSRF check failed"}`, the same for every cause. This is a different message from the permission `403` (`{"detail": "Not permitted"}`), so the client can tell them apart. A request with no session cookie is also this `403` (not `401`), including logout. On this 403 after a login that is still valid (for example the token was lost), call `GET /auth/me` once to refresh the token, then retry once; never loop. Rejected requests are not audited.
- **CORS.** Only `FRONTEND_ORIGIN` may call the API from a browser, with credentials. Allowed methods: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`. Allowed request headers: `Content-Type` and `X-CSRF-Token` (no wildcards), so a client must not add other custom headers.
- **Test for B12.** State-changing calls succeed with the header and fail with `403` without it (see `BD_BACKEND/tests/test_csrf.py` for the backend side).

**Validation error (422) contract:** the custom handler (`app/core/errors.py`, `validation_error_handler`) returns `{"detail": [{"type", "loc", "msg"}, ...]}`. Submitted values (`input`), extra context (`ctx`) and the documentation `url` are intentionally excluded so a rejected password is never echoed. Clients must rely only on `detail[].loc`, `detail[].msg` and `detail[].type`. `openapi.json` still documents FastAPI's default `HTTPValidationError`; checked in A1: it requires exactly `loc`, `msg`, `type`, lists `input` and `ctx` as optional and has no `url` property, so the real response is a compatible subset of the documented schema and generated clients need no change. Done in A7: `openapi.json` now documents every 422 as `ValidationErrorResponse` (`detail[]` with `type`, `loc`, `msg`), so the schema matches the handler exactly and generated clients get the narrow type.

## 17. Git workflow (exactly when to branch, commit, push and merge)

Developers run Git themselves. Claude Code is not allowed to commit, switch branches or push (section 18).

1. **Protect `main`** (repository setting `[SUGGESTION]`): changes only by pull request, one approval from the other developer, `make check` (or, until B5, ruff + pytest) green, squash merge, delete the branch after merge.
2. **Start of every task:** `git switch main && git pull --ff-only`, then `git switch -c m1/<a|b>-<task>` (names in section 14). One task, one branch, one pull request, ideally finished within a day. Never reuse a branch for a second task.
3. **Commit** after every green step, meaning code and its tests together as one logical unit, so each commit passes `ruff` and `pytest` on its own. Message: `type(scope): subject` (for example `feat(leads): add Person and PersonEmail models`), ending with the co-author line when Claude helped. Never commit `.env`, secrets, `.claude/settings.local.json` or real lead data.
4. **Sync before you push, and again before opening the PR:** `git fetch origin && git rebase origin/main`. Rerun ruff and pytest after the rebase. Never `git merge main` into a feature branch.
5. **Push** at the end of every working day and when the task is done: `git push -u origin <branch>` the first time, `git push` afterwards. After a rebase, `git push --force-with-lease` on your own branch only; never `--force`, and never on `main` or on the other developer's branch.
6. **Open the PR** when the task's acceptance items pass locally. Put docs updates (owner table, `FILE_STRUCTURE.md`, `ARCHITECTURE.md`, `USERPROMPT.md` summary) in the last commit. State in the description which gate it clears or waits for.
7. **Review:** the other developer reviews. A review that finds a file outside the author's ownership list blocks the merge.
8. **Merge** (squash) only when approved and green. After merge both developers run `git switch main && git pull --ff-only` before starting the next task.
9. **If a conflict still happens:** stop, tell the other developer, and resolve it in your own branch by rebasing; never edit or push to the other developer's branch. `USERPROMPT.md` conflicts: keep both sides.
