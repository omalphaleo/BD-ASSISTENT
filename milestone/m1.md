# M1: Project setup and data model

Source: `docs/plan.md` §16 (M1), with detail from §6.2 (entities), §6.3 (modeling decisions), §14 (modules A, E, S, T) and §15 (dependencies). Nothing here is new scope. Anything not yet built is "planned".

## 1. Purpose and output
M1 lays the foundation every later milestone builds on. It delivers:
- a running app (backend + frontend skeleton) with working login,
- empty shells for the screens that later milestones fill in,
- the full initial database schema for all modules, reviewed with the business owner.

It contains no business features such as import, search or sending.

## 2. Tasks

| # | Task | What it means |
|---|---|---|
| 1 | Backend skeleton | FastAPI app, settings (`config.py`, fail-fast on missing env vars), SQLAlchemy 2.x and Alembic. |
| 2 | Frontend skeleton | Next.js + TypeScript, with the API client generated from the backend's OpenAPI schema (never hand-edited). |
| 3 | `.env` handling | Environment-variable configuration for both backend and frontend; real `.env` files stay out of git. |
| 4 | Database | PostgreSQL 17 with the pgvector extension, set up on Mac (Docker Compose is also in scope for local dev, decision 0001). |
| 5 | Procrastinate | Job queue with a no-op worker, proving that background jobs run. |
| 6 | Users and auth | `User` with roles, session login, and permission dependencies enforced server-side. |
| 7 | `core.clock` | The single source of time, `now()`, with an admin test offset. Code never calls `datetime.now()`. |
| 8 | Audit module (basic) | Append-only audit log and a `record()` service. Other modules may call it. |
| 9 | Full initial data model | Models and migrations for all modules (see §3). Admin screens follow in M5. |
| 10 | Base layout and login page | Next.js shell and a login page. |
| 11 | Test scaffolding | pytest with factories; Vitest and Playwright set up. |
| 12 | `make check` | One command that runs ruff, pytest, tsc, ESLint and the frontend tests. |

## 3. Data model scope
Models and migrations are created for every app now, even though most screens come later. Key fields only (the full field list is settled in M1):

- **core:** `User` (role, active), `Setting` (key, typed value, version), `ClockOffset`, `JobLock`.
- **imports:** `ImportFile`, `SourceProfile` (three layouts still `[UNRESOLVED]`), `ColumnMapping`, `RawRow` (immutable original values, D-099), `ImportReport`.
- **leads:** `Company`, `Person`, `PersonEmail`, `PersonPhone`, `SocialProfile`, `ContactChannel`, `QuarantineRecord`, `DuplicateCandidate`, `MergeRecord`, `Segment`, `LeadNote`, `LeadEvent`, `Touch`, `LeadStatusFlag`, `IndustryMapping`, `StateMapping`.
- **compliance:** `OptOut` (per email address, D-066), `EligibilitySnapshot` (optional), `ComplianceGateStatus` / `ComplianceChecklistItem` (D-081), `ErasureRecord`.
- **content:** `VoiceSetting`, `SizeProfile`, `IndustryProfile`, `KnowledgeItem`, `KnowledgeEmbedding`, `EmailStructure` + `StructureSection`, `ConfigVersion`.
- **campaigns:** `Campaign`, `CampaignLead`, `EmailSequence`, `EmailDraft`, `ValidationResult`.
- **outreach:** `OutreachMessage` (the persistent send queue), `SendAttempt`, `Mailbox`.
- **mail:** `MailThread`, `OutboxMessage`, `InboundMessage`, `DeltaCursor`, `ReplyClassification`, `BounceRecord`.
- **notifications:** `Notification`, `SlaReminder`.
- **audit:** `AuditLog` (append-only).

Modeling decisions that apply (§6.3):
- Two data layers: `RawRow` is immutable; unified `Person`/`Company` keep the latest values only (D-008). `[AGREED]`
- Email addresses live in their own table (several per person, verification differs). `[AGREED]`
- Soft state instead of hard deletes, except the erase-person flow. `[SUGGESTION]`
- Voice, profiles and structures are versioned through `ConfigVersion` snapshots. `[AGREED]`
- The vector column is sized to the configured Gemini embedding model; model name and dimension are stored with each vector so a model change forces re-embedding. `[SUGGESTION]`

## 4. Modules touched
- **A. Authentication and user management:** backend and model in M1. Screens: login, logout, and (admin) user list and edit, "my profile". Server-side enforcement everywhere; owner-only draft editing; managers read-only.
- **E. Lead and company management:** data model only. Screens arrive in M3.
- **S. Audit and history:** built from M1 and extended each milestone. Audited actions include approval, export, merge, opt-out removal, erasure, settings changes and real-sending activation; role changes, login failures and import deletion are suggested. `[SUGGESTION]`
- **T. Admin settings:** some settings exist earlier (settings store); admin screens come in M5.

Cross-cutting pieces M1 provides to everything else: audit, permissions, test-clock `now()`, settings store.

## 15. Rules that keep the two developers from conflicting

1. **A0 goes first.** It is the only task that touches shared wiring (`app/models.py`, stub packages, `.gitignore`). B starts B1 as soon as A0 is on `main`.
2. **One owner per file** (section 13). If you need a change in a file you do not own, ask the owner to make it in their next PR; do not edit it yourself, even for one line.
3. **New files over edited files.** Each task creates its own test files, factory files and migration, and edits no other task's file. Two PRs that only add different files cannot conflict.
4. **One linear migration chain.** Revisions are fixed up front: A uses `0005` core, `0006` leads, `0007` imports, `0008` compliance; B uses `0009` content, `0010` campaigns, `0011` outreach, `0012` mail, `0013` notifications; `0009`'s `down_revision` is `0008`. B writes its models early but creates migration files only after G1 is merged, then rebases. The single-head test from A0 fails any fork. An applied migration is never edited.
5. **Contracts instead of waiting.** Section 16 lists the A tables that B points at, so B can use string foreign keys before A's code exists. For the API, B builds on the existing `/auth/*` endpoints and the committed `openapi.json`; the CSRF design note from A8 is written in this file before B12 starts.
6. **`USERPROMPT.md` and shared docs.** Both developers append to `USERPROMPT.md`, which would collide on IDs and on the last line. `[SUGGESTION]` (changes the `CLAUDE.md` rule, so it needs agreement and is not applied here): A uses `T-1xx` IDs, B uses `T-2xx` IDs, and a conflict in this file is always resolved by keeping both sides. Other docs follow the ownership table; put doc updates in the last commit of the PR, after rebasing.
7. **Gates (merge order).** A0, then A1; G1 (A5 merged) before B6; A8 before B12; A11 before B11. Everything else runs in parallel.

**API contract:** B generates its client only from `BD_BACKEND/openapi.json`. Today that is `/health`, `/auth/login`, `/auth/logout`, `/auth/me`. Endpoints from A7 and the CSRF header from A8 appear after A regenerates the file; B regenerates the client afterwards (B2 script).

**Validation error (422) contract:** the custom handler (`app/core/errors.py`, `validation_error_handler`) returns `{"detail": [{"type", "loc", "msg"}, ...]}`. Submitted values (`input`), extra context (`ctx`) and the documentation `url` are intentionally excluded so a rejected password is never echoed. Clients must rely only on `detail[].loc`, `detail[].msg` and `detail[].type`. `openapi.json` still documents FastAPI's default `HTTPValidationError`; checked in A1: it requires exactly `loc`, `msg`, `type`, lists `input` and `ctx` as optional and has no `url` property, so the real response is a compatible subset of the documented schema and generated clients need no change. `[SUGGESTION]` Future item (A6/A7, when endpoints declare responses): document the narrowed shape explicitly with a dedicated response model so the schema matches the handler exactly; not done in A1 to keep its scope.

## 17. Git workflow (exactly when to branch, commit, push and merge)

Developers run Git themselves. Claude Code is not allowed to commit, switch branches or push (section 18).

1. **Protect `main`** (repository setting `[SUGGESTION]`): changes only by pull request, one approval from the other developer, `make check` (or, until B5, ruff + pytest) green, squash merge, delete the branch after merge.
2. **Start of every task:** `git switch main && git pull --ff-only`, then `git switch -c m1/<a|b>-<task>` (names in section 14). One task, one branch, one pull request, ideally finished within a day. Never reuse a branch for a second task.
3. **Commit** after every green step, meaning code and its tests together as one logical unit, so each commit passes `ruff` and `pytest` on its own. Message: `type(scope): subject` (for example `feat(leads): add Person and PersonEmail models`), ending with the co-author line when Claude helped. Never commit `.env`, secrets, `.claude/settings.local.json` or real lead data.
4. **Sync before you push, and again before opening the PR:** `git fetch origin && git rebase origin/main`. Rerun ruff and pytest after the rebase. Never `git merge main` into a feature branch.
5. **Push** at the end of every working day and when the task is done: `git push -u origin <branch>` the first time, `git push` afterwards. After a rebase, `git push --force-with-lease` on your own branch only; never `--force`, and never on `main` or on the other developer's branch.
6. **Open the PR** when the task's acceptance items pass locally. Put docs updates (owner table, `FILE_STRUCTURE.md`, `ARCHITECTURE.md`, `USERPROMPT.md` summary) in the last commit. State in the description which gate it clears or waits for.
7. **Review:** the other developer reviews. A review that finds a file outside the author's ownership list blocks the merge.
8. **Merge** (squash) only when approved and green. After merge both developers run `git switch main && git pull --ff-only` before starting the next task.
9. **If a conflict still happens:** stop, tell the other developer, and resolve it in your own branch by rebasing; never edit or push to the other developer's branch. `USERPROMPT.md` conflicts: keep both sides.

### 18.5 How this meets the requirements

| Requirement | Setting that provides it |
|---|---|
| No file created, changed or deleted without approval | `ask` on `Edit`, `Write`, `NotebookEdit`; `deny` on `rm -rf` and destructive Git commands; `defaultMode: default`; bypass mode disabled |
| No unintended changes to secrets, Git data or rules | `deny` on `.env*`, `.git/**`, `CLAUDE.md` |
| No overlapping file edits between developers | per-developer `settings.local.json` fence (18.2) plus the single-owner table (section 13) |
| No Git conflicts caused by Claude | Claude cannot commit, add, switch, merge, rebase or force-push; developers do it (section 17) |
| Settings cannot be weakened quietly | the shared file changes only through a reviewed PR; bypass mode disabled at user level too |
